The training framework, concept by concept

One idea holds the whole project together: training throughput comes down to two things — fitting the model in GPU memory, and never letting the GPUs sit idle. Almost every knob below serves one of those two. Open your answer with this line and everything after it sounds deliberate.

01

What actually lives in GPU memory

In plain English

People think a model "fits" if the weights fit. That's the trap. When you train, the GPU has to hold far more than the weights. Picture four buckets sharing one GPU: the model's weights, a copy of the gradients (one number per weight), the optimizer's memory of each weight, and the activations — all the intermediate numbers from the forward pass that you have to keep around so you can compute the backward pass. The optimizer bucket is sneaky-big, and the activations bucket grows with how big your batch is. So "will it fit" is really "will all four buckets fit at once."

The technical version

For a model with N parameters, training memory is roughly: weights (N), gradients (N), and optimizer state — for AdamW that's two moments per parameter (2N), plus often an FP32 master copy of the weights. That's why a 1.2B model needs several times 1.2B worth of memory before you've stored a single activation. Activations scale with batch × sequence_length × layers and are usually what you trade away first (via gradient accumulation or activation checkpointing). Your 1.2B GPT fits comfortably on one 80GB H100 with room for activations — which is the fact that makes plain DDP the correct choice.

The one-liner

"Fitting a model isn't about the weights — it's weights plus gradients plus optimizer state plus activations, all resident at once. Optimizer state for Adam alone is 2× the parameter count."

02

DDP — how multi-GPU training actually works

In plain English

You've got 8 GPUs and you want them to train one model together. DDP's idea is simple: put a full copy of the model on every GPU, and give each GPU a different slice of the batch. Each one does its own forward and backward pass on its own data, so each ends up with slightly different gradients. Then — the key step — all 8 GPUs get on a call, average their gradients together, and everyone applies the same averaged update. So all 8 copies stay perfectly in sync, step after step. It's like 8 students reading different pages of the same book, then pooling their notes so they all learn the same thing.

The technical version

DistributedDataParallel replicates the full model on each rank. Each rank processes a distinct micro-batch (data parallelism), producing local gradients. Before the optimizer step, gradients are synchronized with an all-reduce — every rank ends up with the averaged gradient. DDP overlaps this communication with the backward pass by bucketing gradients and firing the all-reduce as soon as each bucket is ready, so comms hide behind compute. You launch it with torchrun --nproc_per_node=8, which spins up one process per GPU. Because the whole model must fit on a single GPU, DDP is only valid when it does — which is exactly your case.

If they push

"Does every GPU have the whole model?" — Yes, that's the defining trait of DDP, and its limitation: it scales your throughput, not your model size. The moment the model doesn't fit on one GPU, DDP breaks and you need FSDP (next section).

"What's communicated between GPUs?" — Only gradients, once per step, via all-reduce. Not activations, not weights.

03

FSDP — the answer for models too big for one GPU

In plain English

DDP falls apart when the model itself won't fit on a single GPU — because DDP needs a full copy on each one. FSDP fixes this by refusing to keep a full copy anywhere. Instead it chops the model into shards and scatters them across the GPUs, so each GPU permanently holds only a slice. When it's time to run a particular layer, the GPUs quickly gather just that layer's weights, use them, then throw them away and free the memory. So at any instant, no GPU is holding the whole model — which is how you train something far bigger than one card could ever hold.

The technical version

FSDP (Fully Sharded Data Parallel) shards parameters, gradients, and optimizer state across ranks. For each layer's forward/backward, it does an all-gather to reconstruct that layer's full weights just-in-time, computes, then frees them; gradients are reduced with reduce-scatter so each rank keeps only its shard. The trade versus DDP is more communication (gather/scatter every layer) in exchange for a much lower per-GPU memory footprint. It's the same underlying idea as DeepSpeed ZeRO stage 3.

The one-liner

"I used DDP because a 1.2B model fits on a single H100. FSDP is the first thing I'd reach for to train something that doesn't fit — it shards the model so no GPU holds the whole thing, trading extra communication for lower memory."

04

BF16 mixed precision — and why not FP16

In plain English

A number can be stored with lots of digits (full precision, FP32) or fewer (half precision). Fewer digits means less memory to store and less data to move, which makes training faster — the whole reason we do "mixed precision." But there are two flavours of half precision, and the choice matters a lot. FP16 can store fine detail but has a narrow range — very small or very large numbers overflow or vanish, and gradients in training are often tiny, so they silently disappear. BF16 sacrifices a little fine detail to keep the exact same range as full precision, so nothing overflows and nothing vanishes. On modern GPUs that trade is almost always worth it, which is why BF16 is the default for training big models.

The technical version

Both are 16-bit, but they split the bits differently. FP16: 5 exponent bits, 10 mantissa — more precision, narrow dynamic range, so it needs loss scaling to stop small gradients underflowing to zero. BF16: 8 exponent bits (identical range to FP32), 7 mantissa — less precision, but the wide range means no loss scaling and no overflow drama. In practice you run matmuls in BF16 via autocast while keeping sensitive ops (softmax, layernorm, the loss) and the optimizer's master weights in FP32. The H100 has native BF16 tensor cores, so it's fast and stable.

If they push

"Why BF16 over FP16?" — BF16 keeps FP32's exponent range, so I don't need loss scaling and I don't hit the underflow/overflow issues FP16 has. I give up a little mantissa precision, which doesn't matter for training stability.

05

torch.compile & matmul precision — nearly free speed

In plain English

Normally PyTorch runs your model one small operation at a time, with Python deciding what to do at each step — lots of little handoffs, each with overhead. torch.compile looks at your whole model once, fuses those little operations into a few big efficient chunks, and skips the repeated Python overhead. You change one line and get faster training. Separately, telling PyTorch it's allowed to do its big matrix multiplies slightly less precisely lets the GPU use its dedicated fast-math hardware — again, real speed for basically no downside on a model like this.

The technical version

torch.compile traces the model into a graph and generates fused kernels (via TorchInductor), cutting Python and kernel-launch overhead. torch.set_float32_matmul_precision("high") permits TF32 on the tensor cores for FP32 matmuls — a truncated mantissa that runs far faster with negligible accuracy impact at pretraining scale. Both are throughput wins that don't change your model or math meaningfully.

The one-liner

"torch.compile fuses the op-by-op execution into optimized kernels and removes Python overhead — a one-line change for real throughput. Raising matmul precision lets the tensor cores use TF32, which is faster for a tiny precision cost."

06

Gradient accumulation — a big batch on a small GPU

In plain English

Big models train more stably with a big batch — lots of examples averaged together per update. But a big batch needs a lot of memory, and you might not have it. Gradient accumulation is the workaround: instead of doing one giant batch, you do several small ones back-to-back, add up their gradients as you go, and only do the actual weight update after you've been through all of them. The model can't tell the difference — it's mathematically the same as one big batch — but at any moment you only ever hold one small batch in memory. It's paying in time to buy the effect of memory you don't have.

The technical version

Run grad_accum micro-batches, summing .grad across them, then call optimizer.step() once. Effective batch = micro_batch × grad_accum × num_gpus. It trades wall-clock time (more forward/backward passes per update) for a larger effective batch without the memory cost. With DDP there's a subtlety: you wrap the non-final micro-steps in no_sync() so the all-reduce only fires on the last one — otherwise you'd pay the communication cost every micro-step for nothing. Your config's batch_size: 8, grad_accum: 16 gives an effective batch of 128 per GPU.

If they push

"Is accumulation identical to a real large batch?" — For the gradient, yes (ignoring tiny numeric differences). The cost is throughput: you do N times the passes per optimizer step, so it's slower than if you genuinely had the memory for a batch that size.

07

MFU & the 6ND rule — the number they'll grill

In plain English

A GPU has a top speed — a maximum number of math operations per second it can theoretically do. In real training you never hit that top speed, because time leaks into moving data around, waiting, and overhead. MFU is just: what fraction of the GPU's top speed did I actually use? If your GPU can do 100 units of work a second and your training is effectively doing 40, that's 40% MFU. It's the single cleanest measure of how efficient your training loop is — and around 40% is genuinely good, so it's a number worth stating and defending.

The technical version

MFU (Model FLOPs Utilization) = the useful model FLOPs you achieved ÷ the hardware's peak FLOPs. The useful part uses the 6N rule: training one token costs about 6 × N FLOPs — roughly 2N for the forward pass and 4N for the backward. So:

MFU = (6 · N · tokens_per_sec) ÷ (num_gpus · peak_flops_per_gpu)

H100 BF16 peak ≈ 990 TFLOP/s (dense — NOT the ~1,979 "with sparsity" number)

Plug in your parameter count N, your measured tokens/sec, and the H100's dense BF16 peak. Use 990, not the sparsity-marketing figure, or a sharp interviewer will catch you inflating it.

If they push

"How did you compute 40% MFU?" — Recite the formula above: 6N FLOPs per token times tokens/sec, over GPUs times the H100's 990 TFLOP/s dense BF16 peak.

"What limits MFU?" — Data loading stalls, communication not overlapping with compute, small batches, and memory-bandwidth-bound ops. Pushing MFU up is mostly about keeping the GPUs fed and hiding communication.

08

AdamW vs Muon — the optimizer question

In plain English

The optimizer is the rule for how you nudge the weights after each batch. AdamW is the reliable default everyone uses: for each weight it remembers how the gradient has been trending and how bumpy it's been, and uses that to take smarter steps. Muon is a newer alternative that does something cleverer with the update for the big weight matrices in the model, and often learns from the same data more efficiently. The honest interview move is to explain what each does at a high level and be upfront that Muon is recent — don't pretend to know its deepest internals if you don't.

The technical version

AdamW: Adam with decoupled weight decay. It keeps two running estimates per parameter — first moment (mean of gradients) and second moment (variance) — which is why its optimizer state is ~2N. Muon (Momentum Orthogonalized by Newton-Schulz) orthogonalizes the momentum update for the 2D weight matrices, which tends to improve sample efficiency. Standard practice — and what your repo does — is to use Muon for the hidden matrices and keep AdamW for embeddings, the LM head, and scalar/1D parameters.

If they push (honesty catch)

"Why does Muon work / what's the Newton-Schulz part?" — If you know it: it's an iterative method to approximately orthogonalize the momentum matrix without a full SVD. If you don't: say exactly that — "I used it as a config option and benchmarked it against AdamW; I haven't studied the orthogonalization math deeply." That honesty scores higher than a wrong bluff, every time.

09

Learning-rate schedules & why WSD is nice

In plain English

The learning rate is how big a step you take each update. You don't keep it fixed — you start tiny and ramp up (warmup, so you don't blow up early), then gradually bring it down as training settles (decay, so you fine-tune into a good spot). Cosine and linear are two shapes for that ramp-down. WSD is a different shape that's handy when you might want to continue training later: it warms up, then holds steady for a long stretch, then decays fast at the very end. Because the steady stretch doesn't commit to an ending, you can branch off or add more data from any point in it without having already burned through your learning rate.

The technical version

All schedules start with a warmup (linear ramp from ~0) to avoid early instability. Cosine decays following a cosine curve to a small final LR — the common default. Linear decays straight down. WSD (Warmup-Stable-Decay) warms up, holds a constant LR for most of training, then decays sharply in a short final phase. Its advantage is decoupling schedule from total length: you can checkpoint anywhere in the stable phase and continue or branch — which is exactly why it suits continual pretraining and your multi-stage pipeline.

The one-liner

"WSD keeps the learning rate flat through the middle and only decays at the end, so I can branch or resume from the stable phase without the schedule having already decayed away — ideal for continual pretraining."

10

Checkpointing & auto-resume — the engineering they respect

In plain English

Big training runs go for days, and things crash — a machine dies, something runs out of memory. If a crash sends you back to zero, you've burned days of GPU time. So you periodically save your progress and make the run smart enough to pick up exactly where it left off. The catch most people miss: saving just the weights isn't enough. You also have to save the optimizer's memory, where you were in the learning-rate schedule, and which step you were on — otherwise when you resume, the learning rate is wrong and you re-run data you already trained on. And since these save files are huge, you keep only the last few and delete older ones so the disk doesn't fill.

The technical version

A correct checkpoint saves model weights + optimizer state + LR-scheduler state + the global step count (ideally RNG state and data-loader position too). The step count is what lets the schedule and data pipeline resume consistently — save only weights and you restart at the wrong LR and re-shuffle already-seen data. Your pipeline auto-detects the latest checkpoint and resumes, and does checkpoint rotation — keeping only the last 3 — which is a direct storage-vs-history trade. It also handles PyTorch 2.6+ safe-loading (weights-only deserialization).

If they push

"How does resume avoid re-training on the same data?" — Because the step count (and data-loader position) is in the checkpoint, so it continues from the exact point in the data stream, not from the top.

"Why keep only 3 checkpoints?" — Checkpoints are large; rotation caps disk use. The trade is losing older training history you might have wanted for analysis.

11

Pretrain → mid-train → fine-tune

In plain English

A model is built up in stages, like an education. First, pretraining: read an enormous pile of general text to learn language and broad knowledge — this is the long, expensive part. Then mid-training, also called continual pretraining: feed it more, usually higher-quality or domain-specific text to sharpen it further. Finally fine-tuning: train on task- or instruction-shaped examples so it behaves the way you want. Each stage starts from where the last one left off, and your pipeline chains them automatically — one stage saves a checkpoint, the next detects it and continues.

The technical version

Pretraining: self-supervised next-token prediction over a large general corpus. Mid-training / continual pretraining: further pretraining on higher-quality or domain data, often with a short LR re-warmup — this is where WSD's stable phase pays off. Fine-tuning: supervised training on task/instruction data at a lower LR to adapt behaviour without catastrophic forgetting. Your run_pipeline.sh runs the three sequentially, each stage auto-detecting the previous stage's checkpoint via the resume logic.

The one-liner

"Pretraining learns general language from a huge corpus, mid-training continues on higher-quality or domain data, and fine-tuning adapts behaviour on task data at a lower learning rate — and the pipeline chains all three by auto-detecting each stage's checkpoint."

12

Distributed data loading

In plain English

If all 8 GPUs read the same data, they'd all learn the same thing and you'd gain nothing from having 8. So the data has to be split so each GPU sees a different, non-overlapping slice every step. And it has to be fast: if the data pipeline can't feed the GPUs quickly enough, the GPUs sit there waiting — which is the number-one way your efficiency (that MFU number) quietly tanks. Keeping the GPUs fed is half the battle in training performance.

The technical version

A distributed sampler shards the dataset by rank so each GPU processes disjoint micro-batches — this is what makes data parallelism actually parallel. For throughput, data is typically pre-tokenized and memory-mapped (or streamed) so tokenization isn't on the hot path, with enough loader workers and prefetching that input never stalls the GPU. This ties straight back to the framework's thesis: keeping the GPUs fed is the second half of MFU, right alongside fitting the model.

If they push

"What if data loading is the bottleneck?" — The GPUs idle waiting for input and MFU drops. Fixes: pre-tokenize and memory-map so there's no per-step tokenization, add loader workers, and prefetch batches so the next one is ready before the current step finishes.

13

Batch size scheduling

In plain English

Instead of one fixed batch size the whole way through, you can start small and grow it as training goes on. Early on, smaller, noisier batches actually help the model explore and not settle too fast; later, bigger batches give smoother, more stable updates and better GPU efficiency. Your framework grows the batch over time — doubling it at set intervals — to get the best of both phases.

The technical version

A batch_size_schedule increases the effective batch during training (e.g. a doubling strategy every interval_steps). The intuition: small batches early provide beneficial gradient noise for exploration, while larger batches later reduce variance and improve throughput. In your repo this is realized by scaling gradient accumulation, so the effective batch grows without needing more memory.

The one-liner

"I ramp the effective batch size up over training — small and noisy early for exploration, large and stable later for smoother convergence and better throughput — implemented through gradient accumulation so memory stays flat."
